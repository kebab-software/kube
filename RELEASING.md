# Releasing Kube

## Normal release: one action on GitHub

After the one-time signing setup below, use **GitHub → Releases → Draft a new
release**, create an increasing stable tag such as `v0.2.0` at the current `main`
commit, write release notes, and publish it. No manual package-version edits or
asset uploads are required.

**Publish app release** rebuilds the tagged commit for web, Android, Windows,
macOS, and Linux. It stamps package versions and a monotonically ordered Android
version code from the tag. After every build succeeds, it attaches installers,
the standalone web HTML, SHA-256 checksums, build provenance, and automatic-update feeds.
Installers upload before update feeds so clients are not directed to missing files.

This replaces the earlier “copy latest CI artifacts” workflow. Automatic updates
need correctly versioned installers from the release commit, not the constant
development version of an arbitrary CI build.

Use `vMAJOR.MINOR.PATCH`, with no leading zeroes. Stable versions only are supported
by this release channel. Minor and patch components must be at most 999, and major
at most 2000. Android's version code is `major * 1000000 + minor * 1000 + patch`.
Always increase the version; installed apps reject downgrades.

## One-time Android signing setup

GitHub Actions needs two repository secrets:

- `KUBE_ANDROID_KEYSTORE_BASE64`: the base64-encoded permanent JKS signing key.
- `KUBE_ANDROID_KEYSTORE_PASSWORD`: its store and key password. Key alias: `kube`.

On this Windows workspace, `scripts/setup-android-signing.ps1` can generate the key,
restrict local access, and upload encrypted secrets using the existing GitHub sign-in.
It requires explicit permission to upload private signing material. It preserves
existing repository secrets and refuses to replace a key whose password is missing.
Keep a private backup of `.secrets/` (the keystore and its password record); these
files are ignored by Git. Do not delete or regenerate a signing key used by releases.

Once configured, CI signs every release APK and AAB with that same key. A release
build fails if signing is missing; it never substitutes a debug key.

Earlier CI debug APKs use a different key and contain no updater. Export their
library, uninstall that debug app, install the first signed release APK, then import
the library. Subsequent updates keep app data and do not require reinstalling from
the releases page. Development APKs are not an update channel.

## What updates automatically

| Platform | Behaviour |
| --- | --- |
| Windows NSIS installation | Checks on startup and every six hours while running; downloads automatically; installs on app exit or “Restart to update.” |
| Linux AppImage | Same update behaviour; run the AppImage from a location writable by the user. |
| Android signed release APK | Checks and downloads while running. Verifies SHA-256 and the installed signing certificate. “Install update” opens Android's installation confirmation; Android may first require permission to install updates from Kube. |
| macOS | Automatic installation requires Developer ID signing. Without signing credentials, the app explicitly reports this limitation and offers the release page. |
| Web | Loads the updated web deployment on reload. Uploading a release file does not deploy a website automatically. |

All updater-enabled installations must first come from a release built with this
workflow. Existing older desktop installations need one manual upgrade to get the
updater. Checks require internet access and contact GitHub, not Invidious. No music
history is included. GitHub outages or a release still being built do not interrupt
playback; the user can retry in Settings → App updates. End-to-end installation
requires a device test between two real released versions.

## Optional desktop signing credentials

For macOS, add `MAC_CSC_LINK` (Developer ID Application certificate as base64 P12)
and `MAC_CSC_KEY_PASSWORD` to repository secrets. For notarization also add
`APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, and `APPLE_TEAM_ID`. These credentials
must come from your Apple Developer account; they cannot be generated by this project.
Release CI imports them and enables the macOS updater only for signed builds.
Unsigned macOS users must manually install the first signed build to transition.

Windows Authenticode signing is optional for the current updater configuration.
To enable it, add `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD`. Without a certificate,
Windows installers remain unsigned and may show SmartScreen/unknown-publisher
prompts. Electron-updater still checks release SHA-512 hashes over HTTPS; releases
and repository access must be protected. Android additionally enforces its permanent
APK signature. Never put certificate passwords into source files or workflow logs.

## Testing and recovery

Run **Publish app release** manually with **dry_run** enabled and a prospective tag
(for example `v0.2.0`). It builds and signs packages, validates all installer formats
and update feeds, and uploads `release-preview`; it does not create or change any
release. This tests release packaging, not an installed-device update cycle.

To retry a failed published release, rerun its failed GitHub jobs. For manual upload,
select the release tag in **Use workflow from**, set `release_tag` to that tag, and
disable **dry_run**. The workflow checks that the tag and build commit match. It
replaces generated assets with the same names and keeps unrelated files. Future
releases should be new versions, not replaced binaries under an old version.

Publish releases through the GitHub UI or a credential that can trigger workflows.
Releases made by another workflow's default `GITHUB_TOKEN` may not trigger this
workflow. Immutable releases that disallow adding assets after publication need a
draft-build-publish process instead; this workflow assumes mutable GitHub releases.

Normal CI artifacts expire after 14 days. Once attached to a release, assets are
independent of CI artifact retention. Releases must remain available for installed
clients to retrieve their update feeds and installers.


For each requested feature batch, push the tested changes, publish an increasing stable release with notes covering features and fixes, and verify its attached downloads. The workflow appends a download table using the URLs returned by GitHub. The macOS ZIP is an updater dependency. Users can download the DMG directly. For the web edition, download the HTML and open it in a browser.

Desktop downloads from v0.3.0 use Tauri. The download table links to Kube Desktop for Windows, macOS and Linux. Existing Electron installations use the legacy update feeds. To switch to Tauri, export the library in Settings, install Kube Desktop, then import the backup. The two apps use separate local storage.

Tauri verifies updates with the public key in src-tauri/tauri.conf.json. The corresponding private key is in the TAURI_SIGNING_PRIVATE_KEY repository secret. Keep its private backup safe. The release workflow attaches tauri-update.json after uploading the signed desktop packages.
